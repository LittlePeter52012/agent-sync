# 多智能体工具的能力唯一归属设计

## 状态

待用户审阅的设计稿。本设计修正并扩展
`2026-07-30-plugin-marketplace-dedup-exclusions-design.md` 中仅针对部分插件
去重的旧决策；旧文档中关于插件启用状态检测和可逆回退的机制仍然有效。

## 目标

在同一个智能体产品中，同一项实际能力只保留一个有效的提供方能力包。默认
优先采用覆盖完整、已经启用并经过核验的官方插件或产品原生能力，同时把
Agent Hub 保留为可恢复的后备来源。如果用户明确指定 Hub、本地、远端、
目标工具专用方案或禁用该能力，则用户的明确选择覆盖所有默认优先级。

这是一项适用于全部受支持智能体开发工具的通用规则，不再作为 Cursor 或
Cloudflare 的单独特例处理。

## 用户意图

本设计遵循以下原则：

1. 如果某个已安装的官方商城插件或产品原生插件完整覆盖了 Hub Skill、共享
   MCP、本地 MCP 或目标工具专用集成，则该智能体默认采用官方能力包，并
   屏蔽功能等价的其他来源。
2. 如果用户明确拒绝官方插件，并指定 Hub、本地、远端或目标工具专用来源，
   则该明确选择具有最高优先级。
3. 同一个智能体中的同一项能力，不能同时启用两个相互独立的提供方。
4. 某一个智能体安装官方插件，不得导致其他智能体失去 Hub 后备能力。
5. 在条件优先模式下，官方插件被禁用或卸载后，下一次同步必须自动恢复
   Hub 能力。

## 核心概念

### 能力

能力是用户能够感知的一项操作，或边界紧密的一组操作，例如管理 Cloudflare
资源、检索 Zotero 文献或者编辑 Office 文档。

能力必须按语义和实际操作范围进行核验，不能只看名称。例如，
`cloudflare-local` 与名为 `cloudflare` 的商城插件虽然标识不同，但可能覆盖
同一组 Cloudflare 管理操作。

### 提供方能力包

提供方能力包是一个具有统一所有权和生命周期边界的整体，其中可以包含一个
或多个 Skills、MCP 服务、命令、规则或产品原生工具。同一个官方插件内部的
多个互补 MCP 端点仍属于一个提供方能力包。

例如，官方 Cursor Cloudflare 插件提供的文档、Bindings、Builds 和
Observability MCP 服务属于同一个官方能力包，而不是四个相互竞争的提供方。

### 等价提供方

只有经过审查的能力映射明确声明两个提供方覆盖了相同操作，它们才是等价
提供方。供应商相同、说明文字相似、名称相同或者局部功能重叠，都不能单独
证明它们等价。

### 完整覆盖

如果官方能力包覆盖了映射中 Hub 能力对该目标承诺的全部操作，则视为完整
覆盖。如果只覆盖一部分，应把能力拆分为更窄的操作族，或者继续保留 Hub
能力，直到缺口被解决；不得为了追求表面简洁而静默丢失功能。

### 可信官方提供方

插件出现在商城中，不等于它天然可信。必须核验稳定的插件 ID、发布者或商城
来源、当前启用状态、插件清单以及实际覆盖范围。只有写入已审查能力映射的
插件 ID，才能参与官方能力自动优先。新发现的插件或社区插件在完成核验前，
只能标记为 `unmapped-candidate`，不能自动关闭现有 Hub 能力。

### 所有者

所有者是某项能力在某个目标智能体中唯一选中的有效提供方。所有权按目标
隔离，不得因为一个智能体改变所有者而影响其他智能体。

## 所有权优先级

按照下列顺序解析所有权：

1. 用户对目标智能体和能力作出的明确选择；
2. 已安装、已启用、经过核验且完整覆盖的官方插件或产品原生能力；
3. Agent Hub 管理的能力；
4. 已声明的目标工具专用后备来源；
5. 能力不可用，并给出可执行的诊断说明。

用户的明确选择必须保存为持久策略，而不是一次性命令参数。

只需要以下几种选择模式：

- `auto`：存在合格的官方能力包时使用官方能力包，否则使用 Hub；
- `hub`：明确要求 Hub；如果仍有等价的官方插件处于启用状态，则报告冲突；
- `plugin:<plugin-id>`：明确要求指定产品插件，并屏蔽已映射的 Hub 替代项；
- `target:<provider-id>`：明确要求目标工具专用的本地或远端提供方，并屏蔽
  已映射的其他来源；
- `disabled`：明确保持该能力不可用。

`agent-sync` 可以修改和协调 Hub 所有的文件与配置，但不得静默安装、启用、
禁用、认证或删除产品管理的插件。当 `hub`、`target:*` 或 `disabled` 与当前
启用的官方插件冲突时，验证结果必须指出需要在产品插件管理器中完成的操作，
而不是越权修改插件。

## 策略合同

私有 Agent Hub 保存语义能力映射和目标选择。代表性结构如下：

```json
{
  "capability_ownership": {
    "defaults": {
      "selection": "auto"
    },
    "capabilities": {
      "cloudflare": {
        "hub": {
          "skills": ["cloudflare"],
          "mcp": ["cloudflare-local"]
        },
        "targets": {
          "cursor": {
            "official_plugins": ["cloudflare"],
            "selection": "auto"
          },
          "codex": {
            "official_plugins": [
              "cloudflare@openai-curated-remote"
            ],
            "selection": "hub"
          }
        }
      }
    }
  }
}
```

该结构必须是声明式且不包含秘密信息的。它只记录语义等价关系、期望所有者
和回退行为，不得保存 OAuth Token、请求头、账号标识或插件认证信息。

现有 `plugins.<target>.prefer_marketplace` 策略应迁移到这项合同。迁移期间，
解析器可以在一个兼容版本内继续读取旧结构，但新的策略和说明只使用能力
所有权合同。

## 插件发现

只有在能够可靠证明插件当前已经安装并启用时，才允许自动屏蔽 Hub 能力。
缓存目录的存在不能作为启用证据。

插件位于商城也不能单独证明其可信性：插件发现负责证明当前启用状态，经过
审查的能力映射负责证明可信身份和完整语义覆盖。两项证据必须同时成立。

在产品提供可靠只读来源时，适配器优先使用产品自己的状态：

- Codex：`codex plugin list --json`；
- Claude：产品插件列表或权威的已安装插件状态；
- Gemini CLI：扩展管理器提供的已启用扩展状态；
- VS Code/Copilot：当前选中配置文件中的已启用扩展清单；
- OpenCode：生效配置中的活动插件声明；
- Cursor：现有的当前运行日志或实例化证据，并读取匹配版本的插件清单；
- AntiGravity App、CLI 和 IDE：分别读取各自生效的扩展或插件状态，不把三个
  表面合并为一个目标。

只有在测试样例覆盖启用、禁用、陈旧缓存、配置文件切换和损坏状态之后，才
启用相应适配器。不支持或无法确定的插件状态必须保留 Hub 后备能力，并报告
`plugin-state-uncertain`；不得删除唯一已知可用的能力。

## 解析算法

针对每个目标和已声明能力，依次执行：

1. 读取 Hub Skills、共享 MCP、目标专用允许项、能力映射和用户明确选择。
2. 对该目标只发现一次当前活动的产品原生和商城能力包。
3. 对完全相同的 Skill 名或 MCP 传输身份进行自动精确匹配。
4. 只有经过核验的能力映射才能用于语义等价匹配。
5. 根据所有权优先级解析唯一的期望所有者。
6. 当期望所有者是活动插件或目标专用提供方时，只屏蔽 Hub 所有的替代项。
7. 只协调 `agent-sync` 有权管理的配置。
8. 如果仍有产品所有或目标所有的竞争提供方，报告冲突，不静默修改它。
9. 验证目标最终只有一个所有者，并且所需运行能力完整。

普通同步过程中不得调用隐藏模型。发现新的可能重叠插件后，由当前活动智能体
检查其官方说明、插件清单和实际能力，审核通过后再写入确定性映射。未经审查
的语义相似只能作为提醒。

## 互补工具与重复工具的区别

唯一所有者规则作用在操作族层面，而不是供应商或文件类型层面。

- Codex 原生文档工具与 OfficeCLI 可以同时安装，因为丰富文档创作和跨智能体
  确定性批处理、OpenXML 校验属于不同操作族；但同一个文件的同一次修改仍然
  只能选择一个写入工具。
- `llm-for-zotero` 可以在其专用会话中拥有 Zotero 操作，普通智能体会话则由
  Zotero CLI 负责；同一次操作范围内不得重叠。
- NotebookLM CLI 和 NotebookLM MCP 可以作为两种接口存在，但同一次修改只
  能选择其中一条路线。

如果不能精确说明两种工具的操作边界，则在完成审核前把它们视为潜在冲突。

## 同步与诊断

现有能力解析器继续作为唯一所有权裁决来源。公开命令只增加一个紧凑的所有权
视图，不再创建第二套解析逻辑：

```text
agent-sync ownership [CAPABILITY] [--target TARGET] [--json]
```

输出至少包括：

- 期望所有者和实际所有者；
- 选择来源：默认、用户明确选择、精确身份匹配或已审查映射；
- 活动提供方的证据；
- 被屏蔽的 Hub Skills 和 MCP；
- 仍然活动的竞争提供方；
- 当前所有者消失后将恢复的后备来源；
- 执行位置与远端数据目的地，两者分别说明。

`agent-sync trace`、`status`、`verify` 和 `doctor` 必须消费同一个解析结果，
不得各自推测所有权。

验证状态包括：

- `hub-managed`；
- `plugin-owned:<plugin-id>`；
- `target-owned:<provider-id>`；
- `disabled-by-policy`；
- `unmapped-candidate`；
- `plugin-state-uncertain`；
- `ownership-conflict`；
- `owner-missing`。

一个已声明能力出现两个有效提供方时，受管验证必须失败。未经审核的候选项
必须可见，但不能触发破坏性屏蔽。

## Cloudflare 首次迁移

第一项实际映射如下：

- 能力：`cloudflare`；
- Hub 能力包：Skill `cloudflare` 与 MCP `cloudflare-local`；
- Cursor 官方能力包：插件 `cloudflare`，包括其中的文档、Bindings、Builds
  和 Observability 服务；
- Cursor 选择：`auto`；
- Codex 选择：`hub`，保留现有的“明确不使用 Cloudflare 商城插件”决定；
- 其他当前智能体：在检测到活动官方能力包并完成完整映射前，继续由 Hub
  提供能力。

同步以后，Cursor 只保留官方 Cloudflare 能力包，不再注册 Hub 的
`cloudflare-local`，也不再链接 Hub Cloudflare Skill。其他智能体仍然保留
Hub 后备能力。禁用 Cursor 插件并重新同步后，两项 Hub 组件都应自动恢复。

## 当前机器审计范围

正式迁移之前，对每一个已经配置的智能体目标检查：

- 当前活动的产品原生或商城插件；
- 与 Hub Skill/MCP 重叠的能力；
- 与目标专用 MCP 重叠的能力；
- 已禁用或陈旧的插件记录；
- 配置文件或 Profile 独有状态；
- 用户已经明确指定的所有权选择。

审计可以提出映射建议，但只有经过核验的映射才能进入策略。不得删除无关扩展，
也不得因为供应商相同就推断所有工具可互换。

## 数据与安全边界

能力所有权和数据目的地是两个不同事实：

- 本地注册的 MCP 仍然可能把数据发送给云端 API；
- 官方产品插件可能使用产品管理的 OAuth 和远端服务；
- 本地 CLI 可能在本机保存凭据，同时请求同一个远端平台。

所有权报告必须同时说明执行位置和已知网络目的地。凭据始终由产品管理，不得
进入 Agent Hub 或 `agent-sync`。

## 失败处理与回滚

- 插件证据不可用或含糊：保留 Hub 后备能力并报告。
- `auto` 模式下官方插件消失：下一次同步恢复 Hub 能力包。
- 明确指定的插件所有者消失：不静默替换，报告 `owner-missing`，直到用户修改
  策略或恢复插件。
- 明确指定 Hub，但仍有等价官方插件活动：保留 Hub 期望状态，报告
  `ownership-conflict`，要求通过产品插件管理器禁用插件。
- 能力映射无效：修改目标配置前即停止并报告策略错误。
- 回滚：恢复上一版策略并运行 `agent-sync all`；回滚过程不得触碰产品所有的
  插件文件和凭据。

## 非目标

- 自动安装或卸载商城插件。
- 把插件清单、凭据或本机插件库存发送给隐藏模型。
- 把名称相似的 Skills、MCP、CLI 或原生工具自动视为等价。
- 因为一个目标安装官方插件而全局删除 Hub 能力。
- 让两个接口通过竞速方式同时执行同一次修改。

## 验收标准

1. 每个目标中的每项已声明能力最多只有一个有效提供方能力包。
2. 明确的 `hub`、`plugin:*`、`target:*` 和 `disabled` 选择覆盖默认值，同时不
   影响其他目标。
3. `auto` 模式下，活动且完整映射的官方插件只在本目标中屏蔽全部已映射的
   Hub Skill 和 MCP。
4. 删除或禁用该插件后，下一次同步自动恢复 Hub 能力包。
5. 局部覆盖或未经审查的重叠不得静默关闭 Hub 能力。
6. 仍然活动的竞争提供方产生 `ownership-conflict`，并使受管验证失败。
7. Cursor Cloudflare 最终只保留官方插件能力包；没有等价活动官方能力包的
   智能体继续保留 Hub Cloudflare。
8. Codex Cloudflare 保持明确的 Hub 所有权；如果安装 Cloudflare 商城插件，
   必须报告策略冲突。
9. 每个启用的插件适配器都测试活动、禁用、陈旧、损坏和 Profile 状态。
10. `ownership`、`trace`、`status`、`verify` 与 `doctor` 使用同一解析结果并
    得出一致结论。
11. 连续运行两次 `agent-sync all`，第二次不得产生额外变更。
12. 公共仓库和私有 Hub 的隐私、治理测试全部通过，不得写入插件凭据或账号
    状态。
